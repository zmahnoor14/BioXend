# BioXend Pipeline Notes — Manuscript Methods Section

## 1. Pipeline Entry and Workflow

### Main Entry Point
The pipeline is invoked via `nextflow run main.nf` with the following mandatory parameters:
- `--input`: Path to the user's **Template_open.ods** — a filled Excel/ODS workbook containing all experimental data
- `--prefix`: Prefix for auto-generated compound identifiers (CIDX) — e.g., `HMDM`
- `--xenobiotic_class`: Singular form of the chemical class tested (e.g., `drug`, `pesticide`) — used in auto-generated assay descriptions
- `--outdir`: Output directory for results (default: `results/`)

**Example invocation:**
```bash
nextflow run main.nf -profile docker \
  --input Standards/Templates/Template_open.ods \
  --prefix HMDM \
  --xenobiotic_class drug \
  --outdir results/
```

### Workflow Structure
The workflow (`workflows/bioxend.nf`) orchestrates five sequential processes:

1. **GENERATE_REFERENCE** — reads the Reference sheet, extracts RIDX (reference identifier)
2. **GENERATE_CHEMICALS** — processes the Chemicals sheet using RIDX from step 1
3. **GENERATE_ASSAY** — processes the Microbes sheet independently; outputs ASSAY_MAPPING.tsv
4. **GENERATE_ASSAY_PARAM** — depends on ASSAY_MAPPING.tsv from step 3
5. **GENERATE_ACTIVITY** — depends on outputs from steps 2 and 3 (COMPOUND_MAPPING.tsv and ASSAY_MAPPING.tsv)

Each process runs a Python script from the `bin/` directory that performs data extraction, validation, and ChEMBL file generation.

## 3. Complete Output File List

From a full pipeline run (verified against `results/script_executed/` directory):

1. **REFERENCE.tsv** — ChEMBL deposition format; publication metadata (RIDX, PUBMED_ID, DOI, YEAR, TITLE, AUTHORS, JOURNAL_NAME, etc.)

2. **README.toml** — Submission metadata in TOML format; includes Deposition (names, institutions, links), Dataset (description, goal), and Summary_stats (compound count, assay count, endpoint count)

3. **COMPOUND_RECORD.tsv** — ChEMBL deposition format; one row per compound with CIDX, RIDX, COMPOUND_KEY, COMPOUND_NAME, COMPOUND_SOURCE

4. **COMPOUND_CTAB.sdf** — SDF format with 2D chemical structures (coordinates auto-generated by RDKit); each entry has CIDX property

5. **COMPOUND_MAPPING.tsv** — Intermediate lookup table (not published to ChEMBL); maps Common_Name → CIDX for Biotransformation sheet resolution

6. **ASSAY.tsv** — ChEMBL deposition format; one row per assay with AIDX, RIDX, ASSAY_DESCRIPTION (auto-built), ASSAY_TYPE, ASSAY_ORGANISM, ASSAY_STRAIN, ASSAY_TAX_ID, TARGET_NAME, etc.

7. **ASSAY_MAPPING.tsv** — Intermediate lookup table (not published to ChEMBL); maps user-provided assay_identifier → pipeline-generated AIDX

8. **ASSAY_PARAM.tsv** — ChEMBL deposition format; experimental parameters per assay (AIDX, TYPE, VALUE, UNITS, TEXT_VALUE, RELATION); includes temperature, timepoints, media, controls, biomass, dose, etc.

9. **ACTIVITY.tsv** — ChEMBL deposition format; compound–assay activity links (CIDX, AIDX, TYPE='Biotransformation', TEXT_VALUE/VALUE, ACTIVITY_COMMENT with MIX-MB extensions)

## 4. Automated Computations (chemicals.py)

From a SMILES string in the Chemicals sheet, the following are **automatically computed and validated** by RDKit:

- **SMILES validation**: Each SMILES is parsed by RDKit's `Chem.MolFromSmiles()`. Invalid SMILES are rejected with a warning; rows with missing or invalid SMILES are skipped.

- **2D structure generation**: Molecular coordinates are computed by `AllChem.Compute2DCoords(mol)` and written to COMPOUND_CTAB.sdf.

- **Molecular weight, formula, monoisotopic mass**: Currently validated but **not written to output files** — the COMPOUND_RECORD.tsv is ChEMBL-compliant and does not mandate these fields.

- **InChI / InChIKey generation**: Not currently computed; COMPOUND_RECORD.tsv follows ChEMBL deposition format which relies on SMILES as the chemical identifier.

No automated lookups (PubChem, ChEMBL, etc.) are performed on the SMILES during the chemicals step; all data is read directly from the template.

---

## 5. Automated Lookups (microbes.py)

The `microbes.py` module does **not call external APIs** (NCBI Taxonomy, StrainInfo, etc.) during the pipeline run.

**Taxonomy ID (ASSAY_TAX_ID, TARGET_TAX_ID) handling:**
- If ASSAY_TAX_ID is filled in the Microbes sheet, it is copied to ASSAY.tsv as-is.
- If ASSAY_TAX_ID is blank, a warning is issued but the record is processed (the field in ASSAY.tsv will be empty).
- The code comment notes that a future implementation could call StrainInfo or NCBI Taxonomy API to auto-fetch the TaxID from the organism name, but this is **not yet implemented**.

**No metabolite m/z or retention time lookups**: These are free-text fields supplied by the user in the Biotransformation sheet.

## 6. Identifier Generation

### CIDX (Compound Identifier)

**Definition**: Unique alphanumeric code for each compound in COMPOUND_RECORD.tsv.

**Generation logic** (function `_make_cidx` in chemicals.py):
- If the user provides a `Chemical_identifier` in the Chemicals sheet, that value is used directly.
- Otherwise, CIDXs are **auto-generated sequentially** with a zero-padded width that scales to the dataset size:
  - 1–9 compounds: `PREFIX01`, `PREFIX02`, …, `PREFIX09` (width = 2)
  - 10–99 compounds: `PREFIX001`, `PREFIX002`, …, `PREFIX099` (width = 3)
  - 100–999 compounds: `PREFIX0001`, `PREFIX0002`, …, `PREFIX0999` (width = 4)
  - 1000+ compounds: proportionally larger padding

**Prefix**: Supplied via the `--prefix` parameter (e.g., `HMDM`).

**Example**: For a dataset with 50 compounds and prefix `HMDM`, auto-generated CIDXs are `HMDM001`, `HMDM002`, …, `HMDM050`.

### AIDX (Assay Identifier)

**Definition**: Unique code for each assay in ASSAY.tsv, derived from organism/strain/source metadata.

**Generation logic** (function `_make_aidx` in microbes.py):

The AIDX is **constructed from organism, strain, assay source, and target metadata** using this template:
```
[ASSAY_SOURCE_]ORGANISM[_STRAIN | _community]_Biotransformation[_ACCESSION | _TARGET_NAME]
```

**Rules**:
1. **ASSAY_SOURCE** is prepended (with underscore) if the Microbes sheet ASSAY_SOURCE field is non-empty.
2. **ORGANISM** is always included and slugified (spaces/hyphens → underscores, special characters removed).
3. **STRAIN or community**:
   - If "metagenome" appears anywhere in the organism name (case-insensitive), `_community` is appended.
   - Otherwise, the strain name (slugified) is appended if present.
4. **Biotransformation** is always appended.
5. **Target reference**:
   - If TARGET_ACCESSION is filled, it is appended (slugified).
   - Otherwise, if TARGET_NAME is filled, it is appended (slugified).
   - If neither is filled, nothing is appended.

**Uniqueness and disambiguation**: If two rows would generate the same AIDX (same organism/strain/source/target), a counter suffix is added: `_2`, `_3`, etc.

**Examples**:
- Single-bacteria assay: `Zimmermann_Salmonella_typhimurium_LT2_Biotransformation`
- Community assay: `Zimmermann_gut_metagenome_community_Biotransformation`
- With target accession: `Zimmermann_gut_metagenome_community_Biotransformation_P12345`

The user provides a short identifier (e.g., `assay1`) in the Microbes sheet `assay_identifier` column; this is used by downstream sheets (Experiment, Biotransformation) to reference the assay. The ASSAY_MAPPING.tsv file (created by microbes.py) maps these user keys to the final ChEMBL AIDXs.

### RIDX (Reference Identifier)

**Definition**: Unique code for the publication/reference in REFERENCE.tsv.

**Generation logic**: 
- **User-supplied** in the Reference sheet `Reference_identifier` column.
- No auto-generation; the value is copied directly to REFERENCE.tsv and used by all downstream modules (chemicals, microbes, activity).
- The first row's RIDX is extracted to RIDX.txt and passed to all pipeline steps.
- If RIDX is empty, the pipeline exits with an error.

**Example**: `GutMicrobiomeBiotransformation`, `Immunosuppressants_Microbes`

## 9. Auto-Generated Description Fields

### ASSAY_DESCRIPTION (microbes.py)

The ASSAY_DESCRIPTION field in ASSAY.tsv is **auto-built** from Microbes and Experiment sheet data using contextual templates:

#### Single-Bacteria Template
```
The {xenobiotic_class} is tested on {organism} [strain {strain}] for biotransformation. 
The {xenobiotic_class} is measured [with {instrument}] [over {n} time points between {t_min} 
to {t_max} {unit}] [over oxygen condition: {oxygen}].
```

#### Community Template (triggered when "metagenome" is in organism name)
```
The {xenobiotic_class} is tested on {organism} community [with study accession number {ENA_project} 
and sample accession number {ENA_sample}] for biotransformation. 
The {xenobiotic_class} is measured [with {instrument}] [over {n} time points between {t_min} 
to {t_max} {unit}] [over oxygen condition: {oxygen}].
```

**Bracketed fields** are omitted if empty. The `{xenobiotic_class}` placeholder is replaced with the user-supplied singular form (e.g., "drug", "pesticide"). Experimental context (instrument, timepoints, oxygen) is optionally joined from the Experiment sheet when the Experiment sheet `identifier` column matches the assay's user key or contains "all".

### ACTIVITY_COMMENT (biotransformation.py)

The ACTIVITY_COMMENT field in ACTIVITY.tsv is **concatenated** from:

1. **Base comment** (Biotransformation sheet ACTIVITY_COMMENT column)
2. **Reaction type** (if filled): `"The reaction is {value}"`
3. **Metabolite m/z and retention time** (if filled):
   - Both: `"The Metabolite m/z is {mz} with retention time {rt}."`
   - m/z only: `"The Metabolite m/z is {mz}"`
   - RT only: `"with retention time {rt}."`
4. **Metabolite annotation** (if filled): `"The annotated metabolite is {annotation} with annotation level of {level}"`
   - If level is empty: `"The annotated metabolite is {annotation}"`

All non-empty parts are joined with semicolons (`;`). This concatenation is the MIX-MB extension for rich metadata preservation.

## 10. Intermediate Files (Not Published)

The following files are generated during the pipeline but **not published to the final output directory** (suppressed by `saveAs: { fn -> fn == 'X' ? null : fn }` in modules.config):

- **COMPOUND_MAPPING.tsv**: Common_Name → CIDX lookup (used by biotransformation.py to resolve compounds)
- **ASSAY_MAPPING.tsv**: assay_identifier → AIDX lookup (used by experiment.py and biotransformation.py to resolve assays)

These intermediate files are critical for the pipeline's internal data flow but are not ChEMBL deposition files. However, they are automatically generated in the working directory and can be manually extracted if needed for debugging or auditing.

## 11. Validation and Strictness

Each module performs **mandatory field validation** and optional **strictness checks**.

**Default behavior (--strict not supplied)**:
- Validation errors and warnings are printed to stderr.
- The pipeline continues and completes with exit status 0.

**Strict mode (--strict flag supplied)**:
- If any validation warnings are raised, the affected module exits with status 1, halting the pipeline.
- Validation catches empty mandatory fields, invalid data types (e.g., invalid ASSAY_TYPE codes), and logical inconsistencies.

**Key validations**:
- **chemicals.py**: SMILES validity, mandatory compound fields
- **reference.py**: RIDX presence, at least one of DOI or PUBMED_ID
- **microbes.py**: AIDX uniqueness, ASSAY_TYPE codes (A/F/B/U/P/T), TARGET_TAX_ID when TARGET_ORGANISM is filled
- **experiment.py**: AIDX presence, TYPE in controlled vocabulary, VALUE ↔ RELATION parity
- **biotransformation.py**: CIDX/AIDX resolution, TEXT_VALUE or VALUE presence, ACTION_TYPE codes

## 12. Docker Deployment

The pipeline is containerized in **Docker image `zmahnoor/bioxend:latest`**.

**Nextflow invocation**:
```bash
nextflow run main.nf -profile docker \
  --input ... \
  --prefix ... \
  --xenobiotic_class ... \
  --outdir results/
```

The `-profile docker` flag enables the Docker executor; Nextflow automatically pulls and runs the container for each process.

**Work directory**: By default, Nextflow uses `~/nextflow-work/bioxend/` for intermediate files (configurable in `nextflow.config` via `workDir`).

---

## Summary

The BioXend pipeline is a pure-Python Nextflow workflow that transforms a user-filled Excel/ODS template into ChEMBL-ready deposition files. It orchestrates five processes that read template sheets in parallel and sequentially, cross-linking data via intermediate mapping files (ASSAY_MAPPING.tsv, COMPOUND_MAPPING.tsv). Identifiers are auto-generated deterministically from biological and chemical metadata, descriptions are contextually templated, and all outputs follow ChEMBL deposition standards for submission of microbial biotransformation datasets.
